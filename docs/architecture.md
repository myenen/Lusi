# Architecture

The desktop shell in `src-tauri/` hosts the React application in the platform WebView. Vite serves the UI on loopback during development and bundles static assets into the desktop build. Two commands scoped to the main window load and save the theme, language choice, pane widths, and sidebar state in a small JSON file under the application configuration directory. The packaged build uses a restricted content security policy.

The workspace fills the desktop content area. On macOS, the native title bar is overlaid on the workspace so the system window controls sit above the sidebar. Only the main macOS window can use the drag region. The browser preview reserves the same space on macOS, and Windows uses its native title bar.

The React shell in `src/app/` coordinates folder navigation, search, unread filters, selection, and appearance. It loads the connected Inbox snapshot from the desktop core and opens setup in light Liquid Glass when the account store is empty. The browser preview shows account setup. Fresh preferences default to light Liquid Glass.

The shared `Checkbox` in `src/components/ui/` combines a native input with a themed visual. Notification preferences, message selection, and account setup use this primitive. It retains keyboard and form behavior, and displays the native control in forced-colors mode.

The typed catalog in `src/app/i18n.ts` contains English and Turkish interface text. The desktop reads the preferred OS locale when it loads preferences. The browser preview uses the browser language. Unsupported languages fall back to English.

The theme registry in `src/app/themes.ts` resolves saved theme IDs and follows OS appearance in system mode. Theme stylesheets set colors, radii, spacing, surface effects, and motion through CSS variables. Scoped component rules can refine layout within a theme. Rust stores the theme ID separately from the system, light, or dark preference.

The Rust mail core checks its provider profiles first. The Gmail profile matches `gmail.com` and `googlemail.com` and selects implicit TLS on `imap.gmail.com:993` and `smtp.gmail.com:465` using the full email address. It returns an OAuth provider marker, so setup offers Google sign-in after showing the server settings. Rust opens the system browser for a desktop OAuth client using PKCE S256 and a random state. A temporary IPv4 loopback listener accepts only the matching callback. Rust checks the verified account email against the setup address and verifies both transports with XOAUTH2 before saving the connection. The OS credential store holds the refresh token, and a short-lived memory cache holds the access token. SQLite holds the account settings and inbox snapshot for Gmail. Account Center can reauthorize the same mailbox. Google applies restricted-scope verification to public apps using Gmail’s IMAP/SMTP scope. See [Google desktop OAuth](https://developers.google.com/identity/protocols/oauth2/native-app) and [Gmail XOAUTH2](https://developers.google.com/workspace/gmail/imap/xoauth2-protocol).

For other supported domains the Rust mail core checks the provider’s HTTPS Autoconfig file at `autoconfig.<domain>/mail/config-v1.1.xml` and `<domain>/.well-known/autoconfig/mail/config-v1.1.xml`. Only the domain’s Autoconfig subdomain receives the email address. Requests have bounded time and response size. The app accepts IMAP settings for implicit TLS and STARTTLS and stores the security mode and any advertised username as nonsecret metadata.

If HTTPS Autoconfig yields no usable settings, Lusi tries the domain’s `_imaps._tcp` DNS SRV record. Lusi asks for explicit confirmation when a DNS-discovered server uses another domain. If neither lookup succeeds, setup offers manual TLS settings. The app connects to the selected IMAP server after the user submits the sign-in form.

The Rust mail core verifies the TLS certificate and hostname before sign-in. When STARTTLS is configured, the upgrade must succeed before authentication. Setup takes SMTP settings from the provider’s matching HTTPS Autoconfig entry or from manual input. Rust verifies that SMTP accepts authentication over TLS before committing the account. Schema version 4 stores SMTP connection metadata and a separate encrypted credential bound to the outgoing server settings. Existing IMAP accounts remain readable after migration. SQLite also holds the recent Inbox header snapshot. The snapshot is replaced atomically on refresh. A message key contains its UID and UIDVALIDITY, which the reader checks again before fetching the message. Schema version 8 caches opened message content separately from the Inbox snapshot, keyed by account, folder, UIDVALIDITY, and UID. The cache stores the parsed plain text, sanitized HTML, summary, reply metadata, and attachment descriptors for up to 256 previews per account. Reopening a cached message uses SQLite before obtaining IMAP credentials. When the list shows it as unread, the reader attempts a separate flag update. Attachment payloads still fetch on demand.

Launch with `LUSI_SETUP_DIAGNOSTICS=1` for temporary account setup diagnostics on standard error. Diagnostic events contain stage names, timestamps, SMTP port and security mode, and numeric response codes. Leave the variable unset for normal operation.

Rust encrypts the IMAP password with AES-256-GCM using a fresh nonce and authenticates the account address, host, port, login, and TLS mode with it. SQLite holds the versioned ciphertext and the app data directory holds a randomly generated `credentials.key`, created with owner-only permissions on Unix and protected by the per-user app data directory on Windows. Lusi reads the file automatically. Access to both files is sufficient to decrypt the password, and the key is needed to restore an encrypted account.

Schema version 3 migrates existing passwords on the first operation that needs them. It reads the old credential from the OS store, commits the encrypted record, then removes the old entry. If cleanup is interrupted or denied, Lusi retries it after a later successful decryption. A missing or invalid key for an encrypted account produces a credential error, with the ciphertext preserved.

Schema version 6 migrates the existing account, encrypted SMTP credential, and Inbox cache in one transaction. The active account is persisted separately. Inbox headers use the account ID alongside UIDVALIDITY and UID. Mail IPC commands take an explicit account ID, so switching accounts cannot retarget work already in flight. The reader and folders reload on switch. Drafts remain grouped by account in memory for the current session.

IMAP LIST discovers selectable folders and requests special-use roles on servers that advertise the extension. Lusi localizes folder roles and keeps the original mailbox name for protocol commands. The inbox snapshot remains cached on disk. Other folder headers are loaded on selection. After a message body loads, Lusi marks the matching UID as read and updates the Inbox cache after confirmation. A flag update failure leaves the body visible. Read and star actions use UID STORE after checking UIDVALIDITY. Archive and Trash use the server’s reported folder roles and UID MOVE. Restore moves a message from Trash to Inbox. Schema version 5 adds the star flag to the local Inbox cache.

The composer sends MIME through the authenticated SMTP session. Lettre builds the message and separates Bcc recipients from the message headers. Reply targets use Reply-To or From. Reply all includes the original visible recipients with the connected address and duplicates omitted. SMTP adds validated In-Reply-To and References headers when the original has a usable Message-ID. The forwarding draft quotes the original text. An interrupted SMTP submission can have an unknown outcome and requires user review before retrying. Sent copies follow provider behavior.

The reader parses MIME in Rust and uses an HTML allowlist and a limited set of inline CSS properties. The `.mail-theme` class maps message surfaces, text, accents, and borders to color tokens from the active reader theme. Layout and images retain their original styling. Small MIME-attached raster images referenced by Content-ID are embedded directly. A sandboxed inline iframe has its own Content Security Policy and an opaque origin. Scripts, nested frames, forms, and link navigation are blocked. Opening a formatted message loads remote HTTPS images without a referrer. Plain text remains available from the same MIME response.

The Rust `MessageSummarizer` ranks sentences from sanitized HTML or plain text using recurring terms and English/Turkish signals for requests, decisions, and explicit deadlines. It skips common sign-offs and quoted replies, suppresses repetitive points, and returns up to three original excerpts. The summarizer performs no network requests and does not store summaries. A future local model can produce the same structured response without changing the reader.

The composer keeps drafts in memory and offers rich-text and HTML source modes. The editor sanitizes pasted HTML and source markup before rendering it. Rust applies its own allowlist before sending and derives the plain-text alternative from the same sanitized HTML. The resulting MIME alternative stays together inside the mixed part when attachments are present.

The compose panel docks to the bottom corner and can expand or collapse without remounting the editor. Closing retains the session draft. The discard control confirms before clearing it. The formatting tray edits fonts, text size, color, alignment, lists, and links. The outgoing markup allowlist accepts these text styles and the selected font attributes.

### Inbox synchronization

The Rust worker monitors the active account independently of the window. Startup and manual refresh use the same reconciliation path as the worker. Reconciliation reads the UIDs and flags of the latest Inbox window, fetches headers only for unknown UIDs, and atomically replaces the saved window when it changes. A new UIDVALIDITY starts a new generation. Incomplete responses leave the previous snapshot available. The unread badge uses the server count, and the worker emits Inbox snapshots only to the main window for the active account.

A read-only IMAP IDLE connection wakes reconciliation on changes. The worker bounds each IDLE session, uses two-minute polling when IDLE is unavailable, and backs off after failures up to ten minutes. It releases the idle connection when the active account changes. The mail operation lock is used for reconciliation and is free during IDLE and backoff waits.

### New mail notifications

Reconciliation persists the active Inbox UIDVALIDITY and highest observed UID per account in the same transaction as the header snapshot. The first successful sync and any UIDVALIDITY change establish a baseline. Later syncs deliver newly observed unread messages within the reconciliation window, and saving the cursor before delivery prevents duplicates across restarts. The cursor advances when notifications are disabled, so enabling alerts does not replay past mail.

Rust uses the Tauri notification plugin and reads the local privacy preference before including sender and subject. A notification carries an internal account and message key. On a tap, Rust brings the main window forward, activates the account if needed and sends the reader a targeted event. An older header can be fetched by UID without marking the message as read before the reader opens it. Windows delivers tap events from the on-screen banner.

### Desktop lifecycle

The Rust tray controller hides the main window when it receives a close request and the saved preference allows background operation. The hidden window retains its current view and in-memory drafts, and the existing sync worker continues running. The close behavior requires a registered tray. If tray initialization fails, the window closes normally. Notification taps, macOS Dock reopen events, and tray shortcuts share the window activation path. The tray's manual check wakes the existing sync worker. **Quit Lusi** exits the process and ends synchronization.
